01

บริบท: ทำไมต้องมี C

วันนี้เรามี 3 department MCP + busd + codegraph + browser relay แยกกัน — แต่ไม่มีที่เดียวที่ตอบว่า “ทั้งองค์กรเป็นยังไง”

Before C — Fragmented

ตอบคำถามเดียว ต้องยิงหลายที่

  • ✕
    Health แยกส่วน: CTO ดูได้แค่ CTO, Content ดูได้แค่ Content
  • ✕
    ไม่มี freshness: process ที่รันอยู่อาจเก่ากว่าซอร์สโค้ด (“connected ≠ current”)
  • ✕
    สถานะเขียวหลอก: relay ขึ้นแต่ extension offline = ใช้งานไม่ได้จริง
  • ✕
    Core MCP ไม่ได้ต่อ: tool ภาพรวมองค์กรแบบเดิมหายไป
After C — One Axis

คำถามเดียว · คำตอบเดียว · มีหลักฐาน

  • ✓
    Single pane of glass: overall score + สถานะทุกแหล่งในผลเดียว
  • ✓
    Freshness-aware: เทียบ process start กับ source mtime ทุกครั้ง
  • ✓
    Degraded ต้องเห็น: อะไรพัง อะไรช้า อะไรเก่า ระบุสาเหตุ
  • ✓
    ใช้ซ้ำได้: CEO session, App dashboard, CLI, CI ใช้ schema เดียว
หลักคิด: C ไม่ใช่ “dashboard สวยๆ” — มันคือ contract ของคำว่า “healthy” ที่ทุกแผนกและทุกเครื่องมือต้องตอบตรงกัน ถ้า contract นี้ไม่มี แบรนด์ AXIS ก็เป็นได้แค่โลโก้
02

ข้อ C คืออะไร (ขยายความ)

Read-only aggregation facade — MCP server ใหม่ชื่อ axis-status เปิด tool เดียว axis_status ทำหน้าที่ fan-out ไปยังแหล่งข้อมูลทั้งหมด แล้ว normalize เป็น schema เดียว

C1 · Boundary

อ่านอย่างเดียว

ไม่เขียน ไม่ approve ไม่ publish ไม่แตะ DB ธุรกิจ — เป็น “มาตรวัด” ไม่ใช่ “ผู้ควบคุม”

C2 · Fan-out

ขนาน + มีเพดานเวลา

ทุก source ทำงานพร้อมกัน · budget รวม 2s · source ละ 1.2s · ช้าตัวเดียวไม่ทำให้ทั้งระบบค้าง

C3 · Normalize

คำศัพท์เดียว

ok · degraded · down · unknown — และ unknown ห้ามถูกนับเป็น ok

C4 · Freshness

อายุของคำตอบ

ทุก source แนบ fresh, age_s, process_started_at — กันรายงานจากโค้ดที่ตายแล้ว

C5 · Redaction

ไม่รั่วความลับ

ไม่ log API key · bus secret ถูกตัดก่อนแสดง · รายละเอียดภายในถูกย่อเหลือสิ่งที่ตัดสินใจได้

C6 · Evidence

ตรวจซ้ำได้

แนบ timestamp, latency, source id, tool version — ทุกครั้งที่ตอบ คือหลักฐานหนึ่งชิ้น

ทำไมต้องเป็น MCP server แยก: Core MCP เดิมไม่ได้ถูกต่อใน config ปัจจุบัน และการเปิด core กลับมาจะลาก tool เก่าทั้งชุดมาด้วย แยกเป็น axis-status ทำให้ surface เล็ก ปลอดภัย และ “ติดตั้งได้เฉพาะคนที่ต้องการดูสถานะ”

07

Roadmap & เกณฑ์ผ่าน

ผูกกับบันได 4 ด่าน (D1–D4) ของ SoloCorp OS — ไม่มีด่านไหนข้ามได้ และผู้ทำ ≠ ผู้ตรวจทุกด่าน

C0 · D1 — 1 หน้า

นิยาม contract

ระบุ sources, weights, status vocabulary, timeout budget, สิทธิ์อ่าน และเส้นชัย — Owner/CEO อนุมัติก่อนเขียนโค้ด

C1 · D2 — 50–150 บรรทัด

Aggregator จริง

server ใหม่ + tool เดียว เรียก tool ได้จริง มี run output + exit code ไม่ใช่พิมพ์ตอบ

C2 · D3 — ≥20 งาน

Eval ไม่มี false green

ตารางคาด/ได้จริง/root cause ครอบ: source ล่ม, timeout, process เก่า, relay offline, queue failed, git dirty

C3 · D4 — runbook

คนอื่นรันต่อได้

ติดตั้ง, config, ตัวอย่าง output, วิธีอ่าน warning — คนละคนกับผู้ทำต้องรันซ้ำได้ผลเดิม

C4 · หลังผ่าน

ผูกเข้า config + App

เพิ่ม MCP entry `axis-status`, ใช้ schema เดียวใน App MVP dashboard, เปิด CI drift check

Acceptance Criteria
  • 1
    1 call ตอบครบ 7 sources ภายใน 2s (p95 local)
  • 2
    ทุก source มี status, latency, fresh, timestamp
  • 3
    unknown ไม่ถูกนับเป็น ok — มี warning เสมอ
  • 4
    process เก่ากว่าซอร์ส → fresh=false + แนะนำ restart
  • 5
    ไม่มี secret ใน output/log (ตรวจด้วย redaction test)
  • 6
    D3 20 งานผ่าน และ D4 คนอื่นรันซ้ำได้
