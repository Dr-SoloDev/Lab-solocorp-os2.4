# SOP-07: Cross-Instance Dispatch — ฝากงานข้ามครอบครัว

**Owner:** CEO เทอโบ
**Version:** v1.0 (21 ต.ค. 2569)
**Applies to:** ทุก instance ในครอบครัว SoloCorp — [`docs/FAMILY.md`](../docs/FAMILY.md)
**ที่มา:** PR #19 (fork `darinsupanikorn-rgb`) → Owner รับรอง "หนุมาน" เป็นสมาชิกครอบครัวคนที่ 2

---

## หลักการ

> **โค้ดขึ้นแกนกลาง · อัตลักษณ์แยกสาขา** — ครอบครัวไม่ได้แปลว่าเหมือนกัน แต่แปลว่า **ช่วยกันได้**

ต่าง instance **ไม่มี Central Bus ร่วมกัน** (แยกเครื่อง แยก repo แยก DB)
→ **GitHub คือ bus ข้ามบ้าน** — Issue = ช่องส่งงาน · PR = ช่องส่งผลกลับ

---

## ทิศทาง A — แกนกลาง → พี่น้อง (ฝากงาน)

### Step 1 — เลือกผู้รับที่ "มีเครื่องมือที่จำเป็น"

ห้ามฝากงานที่ทำได้ทุกที่ → ให้ฝากงานที่ **ต้องใช้สิ่งที่มีเฉพาะเขา**
> ดูคอลัมน์ "เหนือกว่าครอบครัวตรงนี้" ใน [`docs/FAMILY.md`](../docs/FAMILY.md)
> ถ้าไม่มีใครมี → อย่าฝาก ให้แก้ที่แกนกลาง หรือขอ Owner

### Step 2 — เปิด Issue

```bash
gh issue create --title "[ฝากถึง <ชื่อ CEO>] <สิ่งที่ต้องการ>" \
  --label "dispatch:to-sister" --label "family"
```

**เนื้อหา Issue ต้องมี 5 ส่วนนี้:**

| # | ส่วน | ตัวอย่าง |
|:-:|:--|:--|
| 1 | **ผู้รับ** | `ถึง: หนุมาน (ดาริน · darinsupanikorn-rgb)` |
| 2 | **ทำไมต้องเธอ** | เหตุผลที่เฉพาะเขาทำได้ (เครื่อง/เครื่องมือ/ความเชี่ยวชาญ) |
| 3 | **งานที่ต้องทำ** | คำสั่ง/ขั้นตอนชัดเจน ให้คนอื่นทำตามแล้วได้ผลเหมือนกัน |
| 4 | **หลักฐานที่ต้องส่ง** | output + exit code + ไฟล์ผลลัพธ์ (ดู contract ข้างล่าง) |
| 5 | **ขอบเขต** | อะไรที่ **ห้าม** ทำ (เพื่อไม่ให้ไปแตะแกนกลาง) |

### Step 3 — เขียน "ขอบเขต" ให้ชัด

งานฝากข้ามบ้าน **ต้องแยกชัดเจนว่าอะไรคือของเขา อะไรคือของแกนกลาง**

```
✅ ขอบเขตที่ดี:
   - แก้/เพิ่มได้เฉพาะในสาขาของคุณ
   - ห้ามแตะ profiles/ rules/ opencode.json ของ upstream
   - ห้าม rename หัวหน้าในไฟล์ที่ส่งกลับมา
   - ถ้าพบว่าโค้ดแกนกลางมีบั๊ก → รายงาน อย่าแก้เอง

❌ ขอบเขตที่มีปัญหา:
   - "ปรับปรุงระบบให้ดีขึ้น"   (กว้างเกิน — เขาจะไปแตะทั้งระบบ)
```

## ทิศทาง B — พี่น้อง → แกนกลาง (ส่งผลกลับ)

### Step 1 — ทำงานในสาขาของตัวเอง
- สร้างสาขาใหม่จากแกนกลางล่าสุด (`git pull` upstream ก่อนเริ่ม)
- ทำงานเฉพาะขอบเขตที่ได้รับ

### Step 2 — ส่งผลกลับเป็น PR

```bash
gh pr create --title "[ผลงานถึง <ชื่อ CEO>] <สิ่งที่ทำ>" \
  --label "dispatch:from-sister" --body "..."
```

**เนื้อหา PR ต้องมี:**

| # | ส่วน | ตัวอย่าง |
|:-:|:--|:--|
| 1 | **ผู้ส่ง** | `จาก: หนุมาน (ดาริน)` |
| 2 | **อ้างอิงงาน** | `ตอบ issue #123` |
| 3 | **หลักฐาน** | output จริง + exit code + path/ขนาดไฟล์ผลลัพธ์ |
| 4 | **สิ่งที่เปลี่ยน** | รายการไฟล์ + เหตุผล |
| 5 | **ขอบเขตที่ไม่แตะ** | ยืนยันว่าไม่ได้แตะอัตลักษณ์/โครงสร้าง upstream |

### Step 3 — หลักฐานต้องอยู่ใน repo

หลักฐาน → `bus/evidence/` (ตาม [`SOP-06`](./SOP-06-certification.md))
> `bus/evidence/` อยู่ใน `.gitignore` → ต้อง `git add -f` (หรือผู้ตรวจ commit ให้)

## Contract หลักฐาน (ข้อบังคับ — ไม่มีหลักฐาน = ยังไม่ผ่าน)

ตาม [`rules/06-certification.md`](../rules/06-certification.md) §3 และ [`SOP-06`](./SOP-06-certification.md):

| ด่าน | หลักฐานขั้นต่ำ |
|:---:|:---|
| **D2** | output การรันจริง (คำสั่ง + **exit code** + ผลลัพธ์) — อยู่ใน repo หรือ evidence |
| **D3** | ตาราง ≥20 แถว ตาม `sop/TEMPLATE-D3-evaluation-table.md` + ลิงก์หลักฐาน |
| **D4** | runbook + ผลรันโดยคน/agent คนละตัว (คนละ instance = คนละตัว ✅) |

**ข้อห้ามเด็ดขาด:**
- ❌ อ้าง "ผ่าน D2" โดยไม่มีไฟล์หลักฐานจริงใน repo
- ❌ อ้างหลักฐานที่อยู่ใน `.gitignore` แล้วไม่ได้ commit
- ❌ ผู้ผลิตตรวจชิ้นงานตัวเอง

> 🔍 **บทเรียนจาก PR #19:** fork หนึ่งประกาศว่า agent ผ่าน D2 แล้ว พร้อมชี้ไปที่ไฟล์หลักฐาน
> ที่**ไม่มีจริงใน repo** → upstream ปฏิเสธส่วนนั้น · ต้องตรวจทุกครั้ง

## ขอบเขตของการฝากงานข้ามบ้าน

| ✅ ฝากได้ | ❌ ฝากไม่ได้ |
|:--|:--|
| งานที่ต้องใช้เครื่องมือเฉพาะของเขา | งานที่ทำได้บนแกนกลาง (ทำเองเร็วกว่า) |
| งานที่ต้องรันบนเครื่อง/OS เฉพาะ | งานที่แตะอัตลักษณ์/โครงสร้าง upstream |
| งานที่ต้องใช้ความเชี่ยวชาญเฉพาะทาง | การตัดสินใจระดับ L5 (Owner) |
| งานที่ต้องการหลักฐานจากเครื่องจริง | งานที่ยังไม่มีใครทำได้จริงเลย |

## Checklist (ผู้ฝากงาน)

- [ ] ผู้รับมีเครื่องมือ/สภาพแวดล้อมที่จำเป็นจริงไหม
- [ ] งานนี้แกนกลางทำเองไม่ได้จริงไหม
- [ ] ระบุผู้รับชัดเจน (ชื่อ CEO + repo)
- [ ] ส่วน "ทำไมต้องเธอ" เขียนจากความสามารถเฉพาะ ไม่ใช่คำขวัญ
- [ ] ขอบเขต "ห้ามทำ" เขียนชัด
- [ ] Contract หลักฐานถูกระบุ (อย่างน้อย D2: output + exit code + ไฟล์)
- [ ] Label `dispatch:to-sister` + `family` ติดครบ

## Checklist (ผู้รับงาน)

- [ ] `git pull` แกนกลางล่าสุดก่อนเริ่ม
- [ ] ทำในสาขาใหม่ของตัวเอง
- [ ] ไม่แตะอัตลักษณ์/โครงสร้าง upstream
- [ ] หลักฐานอยู่ใน `bus/evidence/` + commit เข้า repo
- [ ] PR มี label `dispatch:from-sister` + อ้างอิง issue
- [ ] ผู้ผลิต ≠ ผู้ตรวจ (ผู้ตรวจ = อีก instance)
