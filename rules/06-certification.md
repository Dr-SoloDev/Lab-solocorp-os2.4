# 06 — รับรองชิ้นงาน: บันได 4 ด่าน (Certification Ladder)

> **เมื่อมีชิ้นงานจาก agent — ลำดับ + เส้นชัย + ผู้ตรวจ ทุกด่านต้องครบ**
> เกิดจาก incident 05 ส.ค. 2569: @changful รายงาน "เสร็จครบ 4 commits" แต่ตรวจจริงไม่มี branch/commit/โค้ดใดถูกแก้ — ช่องติกถูก ไม่มีใครตรวจ

## 1. ทำไมต้องมีบันได

- องค์กรมีข้อมูลครบ (profiles, SOUL, rules, SOP) แต่ **ขาดลำดับ** (ขั้นที่ไล่ระดับความยาก) และ **ขาดเส้นชัย** (เกณฑ์ชัดเจนว่าผ่าน/ไม่ผ่าน)
- agent ที่ไม่มีตัวเลข / ไม่มีวัดผล / ไม่มีขอบเขตสิทธิ = **ยังเป็นแค่ demo**
- **ช่องติกที่ไม่มีผู้ตรวจ = ระบบส่งเสริมให้หลอกตัวเอง** — ต้องมีผู้ตรวจแยกจากผู้ทำทุกด่าน

## 2. บันได 4 ด่าน — ห้ามข้ามลำดับ

| ด่าน | ชิ้นงานที่ต้องส่ง | ขอบเขต | เส้นชัย = ผ่านเมื่อ... | ผู้ตรวจ (≠ผู้ทำ) | หลักฐานขั้นต่ำ |
|:---:|:-----------------|:-------|:----------------------|:----------------|:--------------|
| **D1** | โน้ต 1 หน้า: งานนี้ต้องใช้ agent เพราะอะไร | **ห้ามเขียนโค้ด** | ครบ 5 ข้อ (งานคืออะไร / ทำไมต้อง agent / ใช้ตัวไหน+เครื่องมือ / ขอบเขตสิทธิ / เส้นชัยของงานนั้น) | CEO / Owner | ไฟล์หน้าเดียว (เทมเพลต D1) |
| **D2** | agent 50–150 บรรทัด **เรียกเครื่องมือเองได้จริง** | ห้ามเกิน 150 บรรทัด | รันจริงแล้วทำงานหน่วยเล็กจบด้วยเครื่องมือ (อ่าน/เขียน/รัน) — ไม่ใช่พิมพ์ตอบ | test runner / script | output การรันจริง + exit code |
| **D3** | ตารางประเมิน **≥20 งาน**: คาดว่าได้อะไร / ได้จริงอะไร / พังเพราะอะไร | **ห้ามข้าม — ด่านที่โดนข้ามบ่อยที่สุด** | ทุกแถวมีตัวเลข/ผลจริง, failure ทุกอันมี root cause, ไม่ cherry-pick เฉพาะงานที่สำเร็จ | Reality Checker / pipeline-auditor | ตาราง D3 + ลิงก์หลักฐานทุกงาน |
| **D4** | โปรเจกต์ที่**คนอื่นรันต่อได้** | ห้ามขั้นตอนลับ / magic | คนอื่น (agent ใหม่หรือมนุษย์) ตาม runbook รันแล้วได้ผลเหมือนเดิม | คน / agent คนละตัวกับผู้ทำ | runbook + ผลรันของคนอื่น |

## 3. กฎเหล็ก 4 ข้อ

1. **ผู้ผลิต ≠ ผู้ตรวจ** ทุกด่าน — ถ้าผู้ทำติกช่องเอง เส้นชัยนั้นไม่มีค่า
2. **สถานะ default = "ยังไม่ผ่าน"** — จนกว่าหลักฐานตามเกณฑ์จะถูก attach (ไม่ใช่ "รออนุมัติ" ที่พึ่งคนมาเห็น)
3. **ห้ามข้ามลำดับ** — งาน execution (เขียนโค้ด/ใช้เครื่องมือ) ต้องมี D2/D3 ของ agent นั้นก่อนรับงานจริง
4. **รายงาน "blocked" พร้อมหลักฐาน = ผลงานที่ถูกต้อง** / **รายงาน "เสร็จ" โดยไม่มีหลักฐาน = failure ที่ร้ายแรงที่สุด**

## 4. สถานะประจำตัว agent

| สถานะ | ความหมาย |
|:-----:|:---------|
| **D0** | ยังไม่ผ่านด่านใด — **ห้ามรับงาน execution จริง** |
| **D1 ✅** | มีเหตุผล + ขอบเขตสิทธิ ผ่านการตรวจ |
| **D2 ✅** | รันได้จริงด้วยเครื่องมือ (50–150 บรรทัด) |
| **D3 ✅** | มีตัวเลขวัดผล ≥20 งาน (คาด/ได้จริง/พังเพราะอะไร) |
| **D4 ✅** | คนอื่นรันต่อได้ (runbook + ผลรันจริง) |

Registry กลาง: `profiles/CERTIFICATION-REGISTRY.md` — ผู้ตรวจ/CEO เท่านั้นที่อัปเดต

## 5. ตัวอย่าง D3 บรรทัดฐาน — incident @changful (05 ส.ค. 2569)

| # | งาน | คาดว่าได้อะไร | ได้จริงอะไร | ผล | พังเพราะอะไร (root cause) |
|:-:|-----|-------------|-------------|:--:|--------------------------|
| 1 | P0-4..P0-6 (6 จุด) | แก้ permission 6 จุด + test ผ่าน | **0 จุด — ไม่มีโค้ดเปลี่ยน** | ❌ | session ไม่มี bash → confabulate แทนรายงาน blocked |
| 2 | ทดสอบ php -l + suite | test ผ่านทุกจุด | ไม่มีการทดสอบ | ❌ | ไม่มีเครื่องมือรันใน session |
| 3 | Commit 4 ตัว | hash จริงบน branch | ไม่มี branch/commit อยู่จริง | ❌ | รายงานสร้างจากจินตนาการ (ไม่มีหลักฐานผูก) |
| 4 | QA doc | มีไฟล์ QA | ไม่มีไฟล์อยู่จริง | ❌ | ผู้ทำติกช่องเอง ไม่มีผู้ตรวจ |

**บทเรียน:** agent ที่ไม่มีตัวเลข + วัดผล + ขอบเขตสิทธิ = ยังเป็น demo — บันไดนี้คือคำตอบของปัญหา

## 6. การใช้ในชีวิตประจำวัน

- ก่อน dispatch งาน execution → **เช็ค registry** ว่า agent ผ่าน D2 ขึ้นไปหรือยัง
- ถ้าองค์กรยังไม่มีใครผ่าน D2+ → งาน execution ต้องแนบ "D2 test" ไว้ในงาน (ชิ้นงานแรกของทุก agent = mini-agent ของตัวเอง)
- งานเสร็จ → ผู้ตรวจเช็คหลักฐานขั้นต่ำตามด่าน **ก่อน** report ต่อ Owner
- หลักฐานเก็บที่ `bus/evidence/` — ตาม SOP-06
